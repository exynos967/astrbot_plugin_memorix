# 数据库自动迁移

2026-09-05。当前目标 `SCHEMA_VERSION=23`，本次完善迁移流程本身，没有增加数据 schema 版本。

## 触发与边界

`ScopeRuntimeManager.get_runtime()` 在首次需要某个 scope 时在线程池中调用 `build_context()`，其中 `MetadataStore.connect()` 完成迁移后才继续装配服务、启动该 scope 的 TaskManager。插件加载不代表全部尚未使用的 scope 已打开；每个库第一次使用时自动升级。

支持已版本化、核心表指纹匹配的旧库，包括 v8 和 schema 9–22。无版本库还必须具有原有段落/关系的向量索引、创建时间、来源与元数据等历史字段；只凭 `paragraphs` 表名不足以识别。真正的空库直接初始化。更高版本、未知主键/结构和误标当前版本但缺少必需字段的数据库拒绝打开，不自动改造猜测出的结构。

## 迁移协议

1. 对已有文件以只读方式预检，未来版本在建立写连接前拒绝。
2. 获取 SQLite `BEGIN IMMEDIATE` 写锁并重读版本；另一个实例已完成升级时直接返回，不重复备份或升级。
3. 在任何 DDL/DML 前，用独立只读连接调用 SQLite Backup API，保存到 `<metadata目录>/backups/<数据库名>.v旧版-to-v目标版.时间.随机ID.sqlite3`。此方式包含 WAL 中已提交内容；不使用文件复制。校验备份后才继续。
4. 共用 `core_schema.py` 中的新建表定义逐列补齐旧字段，再执行现有增量 schema、原生本地表、关系哈希别名、知识类型归一化和必要的事实回填。
5. 检查必需表/列、SQLite `quick_check` 和 `foreign_key_check`。无效关联报错，不擅自删除历史记录。
6. 写入最终 schema 版本，与所有结构和数据变更一并提交。内部 CRUD 的普通 `commit()` 由 ManagedSQLiteConnection 延迟到外层事务结束。

迁移或校验异常触发整体回滚，启动失败时关闭连接，并报告备份路径；已经完成的备份保留。不通过复制备份覆盖正在使用的数据库进行“自动恢复”。SQLite 事务负责失败/崩溃恢复，备份是额外的人工恢复依据。FTS 属于可重建索引，仍沿用启动后的可选初始化，缺少 FTS5 不阻止核心库升级。

SQLite 的 [Online Backup API 文档](https://www.sqlite.org/backup.html)说明了快照和锁行为。不能在持有写事务的同一连接上执行自身备份；实现使用额外的只读源连接，迁移连接在备份完成前不写入结构或数据。

## 模块与扩展

- `migration.py`：识别、写锁、备份、校验、回滚边界与迁移报告。
- `core_schema.py`：四张核心表的共用定义，新建与历史补列由同一来源生成，避免继续使用“一列存在就跳过整组”的检查方式。
- `schema.py` 及既有增量模块：数据版本的演进；新增版本在这里扩展，入口及离线脚本不需要各自重写迁移流程。
- `MetadataStore`：沿用连接及数据修复 API，调用统一迁移器。`migration_report` 记录本次打开的起止版本、备份路径和修复摘要。
- `scripts/migrate_schema_v8_to_v13.py`：历史命名保留，实际迁移复用 `connect()`；`--dry-run` 只读预检，`--restore` 使用 Backup API 并要求先停止插件。

双向量池分流仍为独立离线操作。此次仅升级 SQLite 数据结构，不自动重写向量池布局。

## 验证

补充用例覆盖 v8/无版本/中间版本自动升级、部分字段已有、重复启动不重复备份、WAL 数据快照、DDL 与数据更新后故障回滚、备份失败、最终校验失败，以及未来/未知/误标版本拒绝。旧兼容模块的隔离夹具明确使用 `enforce_schema=False`，不再将不完整的夹具假装成正常的当前数据库。

只读独立复核确认 managed transaction 能覆盖现有普通 commit，并修正了“当前版本仍需结构预检”的遗漏。对“画像快照表创建晚于 v22 补丁”的疑虑核对了实际调用顺序：`_migrate_schema()` 先调用 `_initialize_tables()`，后者在执行 `apply_schema()` 前创建画像表，因此未按该疑虑改动迁移顺序。

依照用户要求，未运行测试、构建、插件启动或真实数据库迁移。仅进行源码静态检查；新增用例不代表运行时回归已通过。
